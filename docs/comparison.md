# 给同一篇 Word 稿补引文，使用插件能多做什么？

在同一篇五段稿件上，两次使用插件、两次只用普通工具，四个独立的 Codex 会话都找到了正确的论文和页码，都保留了缺乏依据的句子并标明缺证。四份交付都把 190 条记录增至 192 条，在 Word 中保存了四处真实 EndNote 引文、三条文末参考文献。插件组还各把两篇新增论文的 PDF 存入了交付库，普通工具组两次都没有随库附入这两个 PDF。这个小样本能检验具体工作步骤；同一篇稿件反复成功，仍不能估计其他稿件的成功率。

外部去重数据给出另一条采用边界。直接调用插件的记录匹配规则，在卒中和血液学两套数据上自动找回了 93.1% 和 57.6% 的已标注重复对。专门做书目去重的 BibDedupe 在相同数据上分别找回 99.6% 和 83.0%。两者自动接受的记录对中都没有观测到误合并。对于希望找齐大量历史重复记录的维护者，应把下文的漏检和待复核工作量一起考虑。[逐项结果](../benchmarks/record-results.json)

## 同稿、同模型、同桌面

被测版本为插件 v0.1.0。四个会话都使用同一模型 `gpt-6.2-astra`、同一台 Windows 上的 Word 和 EndNote 21，以及逐字相同的任务。每次都从同一组输入文件的独立副本开始。代理自行读文献、找位置、建库和处理 Word，均可编写临时代码、使用本机自动化及公开书目检索服务。普通工具组按指令不打开、不使用引用技能。插件组额外获得本项目的两个技能和配套脚本。各会话未继承评测对话，也未获得答案或预制插入计划。宿主可能展示已安装技能的名称，限制依靠操作指令实施，不能视为技术强制隔离或双盲。DSH 的独立配置缺少 DeepSeek API 凭据，因而本节衡量的是 Codex 代理使用这些技能的表现。DSH 的安装和真实宿主加载另有公开测试。[原始任务、资源与计分规则](../benchmarks/protocol.json) · [发布版本](https://github.com/Spark-xY6/dsh-plugin-endnote-cwyw/releases/tag/v0.1.0) · [DSH 与 Word 发布验收](evaluation.md)

### 重开后能否删引文并再次插入

预定挑战只删除 Wilson，刷新书目并保存，再在同一位置插回同一篇论文，刷新、保存并重开。预期正文引文处数为 4 → 3 → 4，文末篇数为 3 → 2 → 3。A、C 求解会话在各自的测试副本中实际完成了这一操作。独立评测者核实四份交付稿的起始状态，第一次统一重测遇到 Word 自动化异常。修订后的测试程序已通过代码审查，桌面同时存在另一项工作的文献库时暂停执行。此时统一的编辑挑战在四组中均未计分。另一个固定计划示例已有完整的原生删引与重插记录。[固定计划原生编辑证据](evaluation.md) · [四组实物核查计数](../benchmarks/manuscript-results.json)

### 怎样复现同一篇稿件

1. 从本机合法安装的 EndNote 21 示例中恢复 `Sample_Library_21.enlx`，取包含 190 条有效记录和 2 条回收站记录的这一版。建一篇独立的 Word 文档，按冻结答案中的五个英文原句逐段写入。第一段在 Wiegrebe 的蝙蝠声呐论述后，用 EndNote 原生插入 Wiegrebe（2008）的真实引文并应用 Nature 样式。本次示例库中的原始记录号是 60，复现时应核实论文身份。[原句、旧文献与三处新引文的评分标准](../benchmarks/predeclared.md) · [Wiegrebe 论文](https://doi.org/10.1007/s00422-008-0216-2)
2. 从出版商取得三篇 PDF，将 Sandve 命名为 `article-01.pdf`，复制同一字节为 `article-04.pdf`。Wilson 为 `article-02.pdf`，Gorresen 为 `article-03.pdf`。因此四个文件只对应三篇论文，其中 Gorresen 是干扰项。稿件内容为评测专门撰写，仓库仅分发原句、标识和校验材料。重建 DOCX 时 Word 可能重新分配内部标识，应另存新副本并重新核验现有引用。[Sandve](https://doi.org/10.1371/journal.pcbi.1003285) · [Wilson](https://doi.org/10.1371/journal.pcbi.1005510) · [Gorresen](https://doi.org/10.1371/journal.pone.0205150) · [原始输入文件清单及 SHA-256](../benchmarks/source-manifest.json)
3. 每个会话只交付 PDF 文件夹、旧库和部分已引文的稿件。将协议中的同一条英文请求发给两组，答案与其他会话输出对两组均保密。预定正确位置是随机种子句引 Sandve 物理第 3 页、整洁数据表句引 Wilson 第 5 页、绘图数据保存句再引 Sandve 第 3 页。最后一句声称一项涉及 240 家实验室的试验将耗时减少 73%；本次给出的 PDF 无此依据，应保留文字、不给引文并说明缺证。页码从 PDF 第一页算起。[协议全文](../benchmarks/protocol.json)
4. 评测者用副本逐段核查正文、字段中的论文身份、库中新增行、旧记录与附件，并在桌面 Word 上执行前述删除和重插。每个会话的选文与实物交付分别评分，即使只有计划，也能单独记录选文表现。重复次数为每组两次，独立稿件数为一。未对四次结果做显著性检验。

## 探索性附加试验换用了另一个真实 EndNote 库

首轮交付后另行冻结了换库试验，保留同一原稿和四份 PDF。评测者在 EndNote 21 中新建独立库，使用官方导入功能写入 60 条记录。关库后的核验确认，原稿里的 Wiegrebe 记录号 60 在新库里指向 Gorresen。正确的 Wiegrebe 是第 1 号。第 2 号是把 `Computational` 写成 `Computation` 且缺 DOI 的 Sandve。库中另有 57 条无关记录，缺少 Wilson。两个独立会话获得的 8 个输入文件逐一字节相同。冻结的目标库数据库 SHA-256 为 `aba73fd86e77b64b8a7709fe93ce55d7e3c5eaa8600a3116bfcc3afc626a305f`。[附加试验协议](../benchmarks/extension-protocol.json)

预定成功条件是把原引文改绑到 1 号，两个位置都复用 2 号，仅为 Wilson 新增一条，将库从 60 增至 61。这个构造同时考验跨库号码碰撞和近似题名，矛盾 DOI 另有代码回归测试。该试验在看过主试验的初步交付后设计，仍只涉及同一篇稿件。

插件会话 F 找对了三处文献、页码和缺证句。宿主没有识别到一次局部辅助脚本的审查凭据，评测者另行审查了求解者指定的原生入口。建库过程中已实际观察到同一 EndNote 进程出现另一个库窗口。代码复核发现 v0.1.0 的导入依赖当时活动的库，清理阶段可能向该进程下其他有标题的库窗口发关闭消息。在共享桌面上停止执行，F 的八份输入哈希全部保留，交付数为零。这里记录的是操作风险和停止决定，没有观察到其他库遭到写入。普通工具组 E 的独立交付仍在核验。固定选择文件的 SHA-256 为 `585ee9abacf98c1279e88965c5f8224da8506a1445411ab407aaee61c20d6ed0`。终止的运行保留原始得分，后续版本需单独验收。

## 三个现成工具在相同稿件上能走到哪一步

我们运行了下表所列的原版入口。每个工具首先收到原稿副本，只有首段存在正式引用。随后按照工具擅长的输入形式，由操作者在三个正确位置提供标记或文献标识，最后一句一直不加标记。后者是阳性对照，用于判断入口能否完成其声明的转换。三个工具都没有在该对照中被要求独立审查没有标注的主张。Windows 环境使用 Python 3.13.9、python-docx 1.2.0 和 requests 2.32.5。

| 工具及本次固定源码 | 原稿直接交给入口 | 给出它需要的输入后，磁盘上得到了什么 |
|---|---|---|
| [PubMate 0.2.5](https://github.com/jgassens/PubMate/tree/f6f3492c0ad2ff8adbb2869043b22b8bd00688fd) | `pmid2endnote` 只发现已有 Word 标记中一处受保护的 DOI，跳过它并写出报告，正常退出。 | 操作者在三处写入两个公开 DOI，并选用 `--doi-source crossref`。得到三处临时引文和一个包含两条 DOI 记录的 ENW 导入文件。旧引文字段仍在。 |
| [endnote-insert](https://github.com/matsuikentaro1/endnote-insert/tree/34b2dc3c44efaa8bacb7a5c329845d5b9d2403c1) | 调用未改动的 `endnote_inserter.process_batch`，传入空标记映射。替换 0 处，DOCX 解包后各成员内容与输入相同。 | 操作者加入 `[2]、[3]、[2]`，提供两个映射（Sandve 的 PMID 24204232、Wilson 的 PMID 28640806）及旧引文中的库标识。生成三处 `EN.CITE`，嵌入的题名和 DOI 正确；字段取 PMID 作为记录号，这两个号及这两篇新论文均不在冻结旧库。磁盘上的文末表仍是原稿的文末表。 |
| [endnote-word-cwyw-skill](https://github.com/lizhbei1995/endnote-word-cwyw-skill/tree/38f34fc27cd4b21305017578eed3b72263b53e82) | `docx_to_endnote_temp.py` 在原稿里没有找到其所需的独立 `References` 标题，退出码 1，未生成 Word 或 RIS。 | 操作者加同样的三个数字标记，并另附标题和两条含 DOI 的编号文献。使用 `--ris`，不预设新记录号。得到三处临时引文和两条 RIS 记录，正文中仍只有原先一个正式引文字段。|

原稿与阳性对照的差别由操作者引入，因此不能把“给定三个正确位置后的三个结果”解释为自动找到了三个位置。PubMate 的 ENW 和第三项的 RIS 中，均核实是两条不同、与期望匹配的 DOI；endnote-insert 的三个新字段只改动了 `word/document.xml`。第三项输出的同一 XML 中，`mc:Ignorable` 列出的 8 个命名空间前缀失去声明，本次没有在该输出上测 Word 的实际响应。这三项比较的终点均为独立程序写出的文件，后续人工导入、官方插件刷新和编辑表现都未纳入计分。各入口已有的功能可直接复用，手动流程能否完成整案需单独实测。

本项目把这些步骤连到同一次交付。代理先用原文页证据选位置，再把论文与指定库中的真实记录对齐，在库副本只导入缺项，最后用官方 Word 插件格式化并验证 Word 和文献库。两次插件交付中，库的附件索引都将新引论文链接到对应的本地全文，两份附件与输入 PDF 的 SHA-256 一一相同。临时引文转换、标记映射和记录去重已有成熟实现。普通代理也能在此次桌面环境中自行写出完成引文和书目交付的流程。[开源方案调研与采用关系](landscape.md)

## 在两个公开书目数据集上漏掉多少重复，误合并多少？

在 CoLRev 的 LDD 基准固定版本中，事先约定按未分片 `records_pre_merged.csv` 文件大小选最小的两个数据集，入选的是 `stroke` 和 `haematology`。它们分别是卒中和血液学综述检索得到的书目记录，统计单位是两条书目记录组成的一对。保留全部 1,292 和 1,415 条，未按字段完备性过滤。每组 `n` 条记录有 `n × (n − 1) / 2` 个无序对，分别是 833,986 和 1,000,405 对。金标准文件 `merged_record_ids.csv` 中每个分号分隔的同篇记录组展开为所有两两组合，得到 479 和 165 个已标注重复对。这里以公开标注作为参照。[固定数据版本](https://github.com/CoLRev-Environment/ldd-full-benchmark/tree/f623ff8a4866defcaaa90021e3a8c916947dd91e) · [计分脚本](../benchmarks/compare_records.py)

| 数据集及金标准重复对 | 方法 | 自动判同篇 | 判对 TP | 误合并 FP | 漏检 FN | 查准率 | 召回率 | 待复核中确属重复 / 待复核总对数 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 卒中，479 | 本插件逐对判定 | 446 | 446 | 0 | 33 | 100% | 93.11% | 19 / 57 |
| 卒中，479 | BibDedupe 最终分组 | 477 | 477 | 0 | 2 | 100% | 99.58% | 2 / 104 |
| 卒中，479 | BibDedupe 直接判同篇 | 477 | 477 | 0 | 2 | 100% | 99.58% | 2 / 104 |
| 血液学，165 | 本插件逐对判定 | 95 | 95 | 0 | 70 | 100% | 57.58% | 23 / 136 |
| 血液学，165 | BibDedupe 最终分组 | 137 | 137 | 0 | 28 | 100% | 83.03% | 28 / 633 |
| 血液学，165 | BibDedupe 直接判同篇 | 135 | 135 | 0 | 30 | 100% | 81.82% | 30 / 635 |

查准率 = TP / (TP + FP)，表示判为重复的记录对中有多少对正确。召回率 = TP / (TP + FN)，表示金标准重复对中有多少对被自动找回。以血液学的插件结果为例，自动接受 95 对，95 对都对，故查准率是 95/95；金标准有 165 对，召回率是 95/165。进入待复核队列的 136 对里有 23 对属于这 70 个漏检，另有 47 个真重复对连待复核队列也没进入。待复核结果没有计入自动判对。[机器可读计数和输入哈希](../benchmarks/record-results.json)

插件直接调用 v0.1.0 的 `reference_identity.compare`，遍历所有记录对，题名、首作者、年份、期刊、卷页及 DOI/PMID 等规则沿用发布版本；结果为模糊或矛盾的两类单列待复核。BibDedupe 0.11.0 按其正常流程执行 `prep → block → match`，再用 `get_connected_components` 产生最终分组。直接判定只计两条记录之间明确标为重复的配对。分组口径还计入同一组里的其他配对，例如 A–B 和 B–C 同组后计入 A–C；血液学中因此多找回 2 对。每种口径的待复核数均剔除同一口径已自动接受的配对。评测没有调阈值、删除记录、写入 EndNote 或修改任何稿件。这是记录匹配组件的只读比较，未测 PDF 元数据抽取、导入拦截或最终 Word 去重的总体正确率。[BibDedupe 用法与分组规则](https://colrev-environment.github.io/bib-dedupe/usage.html) · [BibDedupe 方法论文](https://doi.org/10.21105/joss.06318)

### 在 Windows 复算四个 CSV

从包含 `benchmarks/` 的本仓库检出目录运行，在仓库外新建自己的结果目录。下面只下载选中的四个数据文件。脚本会逐一检查与公开清单一致的 SHA-256，验证记录 ID 唯一、分组 ID 有效，使用一个 CPU 工作进程。示例中的 `$data` 路径可以更换。[数据指纹与原始计数](../benchmarks/record-results.json)

```powershell
$data = Join-Path (Split-Path -Parent (Get-Location).Path) 'ldd-comparison-data'
$revision = 'f623ff8a4866defcaaa90021e3a8c916947dd91e'
$raw = "https://raw.githubusercontent.com/CoLRev-Environment/ldd-full-benchmark/$revision"
foreach ($study in 'stroke','haematology') {
    $dir = New-Item -ItemType Directory -Path (Join-Path $data $study) -Force
    foreach ($file in 'records_pre_merged.csv','merged_record_ids.csv') {
        Invoke-WebRequest "$raw/$study/$file" -OutFile (Join-Path $dir.FullName $file)
    }
}
```

测试所用 pandas 为 2.3.3、BibDedupe 为 0.11.0，`tqdm` 由 BibDedupe 依赖安装。推荐在独立的 Windows Python 环境里运行，脚本会导入 Windows 版插件的书目匹配模块。输出文件应是一个新路径。

```powershell
python -m pip install "bib-dedupe==0.11.0" "pandas==2.3.3"
python benchmarks/compare_records.py --data "$data" --output (Join-Path $data 'record-results.json')
```
